# 혼잡 우회 여행 코스 추천 서비스 '한적' 설계문서 (v3)

- 공모전: 2026 관광데이터 활용 공모전 — 웹·앱 구현 부문
- 지정과제: 2번. 유명 관광지 중심의 관광객 쏠림 현상으로 인한 특정 명소의 오버투어리즘(과밀화) 문제
- 작성일: 2026.07 (v3 개정: 2026.08)
- 개발 인원: 1인 (풀스택)

> **v3 개정 사유**: 한국관광공사 「2026 OpenAPI 서비스 소개」(2026.05) 설명회 자료 검토 결과 반영.
> 주요 변경 — ① 폐기 예정 코드 체계 교체 ② 원천/파생 데이터 분리 ③ 로컬서버 저장 신청·동기화 계획 신설
> ④ 운영계정 전환 절차 일정 반영 ⑤ 집중률 커버리지 제약 명시.
> 변경 이력은 부록 A 참조.

## 1. 서비스 개요

### 1.1 서비스 정의

한국관광공사 관광지 집중률 예측 및 연관 관광지 데이터를 활용해 과밀 명소의 혼잡도를 방문 시점 기준으로 진단하고, 한적한 대안 관광지 중심의 우회 여행 코스를 추천하는 웹 서비스.

### 1.2 타깃 사용자

인파를 피해 여유롭고 쾌적한 여행을 즐기고 싶은 자유여행객 (20~40대, 모바일 웹 중심)

### 1.3 핵심 사용자 시나리오

1. 사용자가 가고 싶은 명소(예: 경주 황리단길)와 방문 예정 시점(날짜/시간대)을 입력
2. 서비스가 해당 명소의 예측 집중률을 조회해 혼잡도 등급(여유/보통/혼잡/매우혼잡)을 진단
3. 혼잡 판정 시, 연관 관광지 중 집중률이 낮고 이동 가능 거리 내에 있는 대안 관광지를 추천
4. 원 목적지 + 대안지를 조합한 우회 코스(방문 순서 + 시간대 배치)를 생성
5. 지도 위 코스 시각화 + 장소별 상세 정보(TourAPI) 제공

### 1.4 차별화 포인트

- 단순 "한적한 곳 추천"이 아니라, 방문 시점(시간대) 기반 혼잡도 예측을 코스 순서 배치에 반영
  (예: 오전엔 한적한 A, 명소 B는 집중률이 떨어지는 오후 4시 이후 방문 제안)
- 공공데이터 3종(집중률 예측 + 연관 관광지 + 관광정보)의 융합 활용
- LLM 기반 코스 설명문 생성으로 "왜 이 코스인지" 근거를 자연어로 제공

### 2.1 데이터 커버리지 제약 (신규)

집중률 데이터는 **10,731건**으로, 국문 관광정보 전체(264,396건) 대비 약 4% 수준이다.
즉 **모든 관광지를 진단할 수 있는 것이 아니라, 집중률 데이터가 존재하는 부분집합에 한정**된다.

설계 반영 사항:

- `attraction` 테이블에 `has_congestion_data` 플래그를 두고, 검색 결과에서 진단 가능 여부를 구분 표시
- 6.2 대안지 매칭의 "집중률 조인" 단계를 통과할 수 있는 후보도 이 집합 내로 제한됨
- 커버리지 밖 관광지 검색 시: 진단 불가 안내 + 인근 커버리지 관광지 제안으로 폴백
- 반대로 연관 관광지는 169만 건(관광지당 평균 150건 이상 추정)으로, 후보 고갈 리스크는 낮음 (11장 리스크 등급 하향)

> **미확인**: 10,731이 *관광지 수*인지 *레코드 수*(관광지 × 날짜 × 시간대)인지 자료상 불분명.
> 반려동물 동반여행 건수와 수치가 동일한 점도 확인 필요. → 1주차 스파이크 항목.

### 2.2 데이터 취득 경로 제약 (신규)

공사 자료 명시 사항: **"맞춤형 데이터 다운로드로 정보를 받아 사용한 것은 공모전에서 OpenAPI 활용으로 인정받지 못함"**

따라서 개발 편의를 위한 CSV/일괄 다운로드 경로를 사용하지 않는다.
목업·시드 데이터도 반드시 **OpenAPI 호출 응답을 저장하는 방식**으로만 생성한다.

## 3. 시스템 아키텍처

```
[사용자 브라우저]
      │ HTTPS
      ▼
[Next.js (App Router)] ── Vercel 배포
      │ REST (JSON)
      ▼
[Spring Boot 4 API 서버 (Kotlin, Spring Modulith)] ── Docker, 클라우드 VM 배포
      │
      ├── [Redis]          집중률/추천 결과 캐시
      ├── [PostgreSQL + PostGIS]
      │        ├─ raw_*      원천 데이터 (무가공 보존)
      │        └─ derived_*  파생 데이터 (등급화·정규화·스코어)
      │
      ├── [배치 스케줄러 (Spring Scheduler)]
      │        └─ A: 집중률 예측 원천 적재 (일 1회)
      │        └─ B: 관광지 마스터·연관관계 동기화 (주 1회)
      │        └─ C: 파생 테이블 재계산 (원천 적재 직후)
      │        └─ D: 호출 실적 집계 (월 1회, 공사 제출용)
      │
      └── [외부 API]
               ├─ 한국관광공사 집중률 예측 API (집중률조회)
               ├─ 연관 관광지 API (지역기반관광정보 / 키워드검색)
               ├─ TourAPI 4.0 (KorService2)
               └─ Claude API (코스 설명문 생성, 선택 기능)
```

설계 원칙:

- 외부 API는 사용자 요청 경로에서 직접 호출하지 않는다. 배치로 DB에 적재된 데이터를 조회하는 구조로, 공공 API 트래픽 제한·장애로부터 서비스 응답을 분리한다.
- 배치 미적재 데이터 요청 시에만 fallback으로 실시간 호출(CompletableFuture 병렬) + Redis 캐싱.
- **원천 데이터는 절대 수정하지 않는다.** 가공이 필요한 모든 값은 파생 테이블에 별도 생성한다 (5.1 참조).

## 5. 데이터 모델 (ERD)

### 5.1 원천 / 파생 분리 원칙 (신규)

공사 FAQ 명시 사항: **"원천 데이터를 수정하는 것을 권장하지 않습니다. 수정 시 해당 콘텐츠로 인한 분쟁 발생 시 책임은 개발사가 부담"**

이에 따라 테이블을 2계층으로 분리한다.

- `raw_*` : API 응답 필드를 **무가공으로** 저장. 컬럼명도 API 필드명 유지. UPDATE 금지, 재적재는 UPSERT.
- `derived_*` : 등급화·정규화·스코어 등 서비스 로직 산출물. 원천 재적재 없이 재계산 가능.

부수 효과: 6.1의 등급 컷을 실데이터 분포 확인 후 조정할 때, 파생 테이블만 재계산하면 된다.

### 5.2 스키마

```
raw_attraction (관광지 마스터 — 원천)
├─ content_id      VARCHAR PK  -- TourAPI contentId
├─ title           VARCHAR
├─ ldong_regn_cd   VARCHAR  -- 법정동 시도 코드  ※ 구 areaCode 대체
├─ ldong_signgu_cd VARCHAR  -- 법정동 시군구 코드 ※ 구 sigunguCode 대체
├─ lcls_systm1/2/3 VARCHAR  -- 분류체계 3Depth  ※ 구 cat1/2/3 대체
├─ content_type_id VARCHAR
├─ mapx, mapy      NUMERIC  -- API 원본 좌표 (문자열 그대로 보존)
├─ firstimage      VARCHAR
├─ overview        TEXT
└─ synced_at       TIMESTAMP

derived_attraction (서비스용 파생)
├─ id              BIGINT PK
├─ content_id      FK → raw_attraction
├─ location        GEOMETRY(Point, 4326)  -- PostGIS, GIST 인덱스
├─ has_congestion_data BOOLEAN            -- 집중률 커버리지 여부
└─ updated_at      TIMESTAMP

raw_congestion (집중률 예측 — 원천)
├─ id             BIGINT PK
├─ content_id     VARCHAR   -- ※ 식별자 체계 검증 필요 (11장 R1)
├─ forecast_date  DATE
├─ time_slot      VARCHAR   -- API 스펙 확인 후 확정
├─ concentration  NUMERIC   -- 원본 집중률 수치 (무가공)
└─ UNIQUE(content_id, forecast_date, time_slot)

derived_congestion (등급화 파생)
├─ id             BIGINT PK
├─ attraction_id  FK → derived_attraction
├─ forecast_date  DATE
├─ time_slot      VARCHAR
├─ percentile     NUMERIC   -- 분포 대비 백분위
├─ grade          VARCHAR   -- 여유/보통/혼잡/매우혼잡 (내부 등급화)
└─ UNIQUE(attraction_id, forecast_date, time_slot)

raw_related (연관 관광지 — 원천)
├─ id                  BIGINT PK
├─ base_content_id     VARCHAR
├─ related_content_id  VARCHAR
├─ relation_score      NUMERIC  -- ※ API 제공 여부 검증 필요 (11장 R2)
└─ UNIQUE(base_content_id, related_content_id)

course (생성된 코스, 공유용)
├─ id           BIGINT PK
├─ uuid         VARCHAR  -- 공유 링크용
├─ target_date  DATE
├─ created_at   TIMESTAMP
└─ course_item (1:N)
     ├─ course_id, attraction_id
     ├─ visit_order  INT
     ├─ time_slot    VARCHAR
     └─ reason       TEXT  -- 배치 사유 (LLM 생성 or 규칙 기반)

api_call_log (호출 실적 — 신규)
├─ id             BIGINT PK
├─ operation      VARCHAR  -- 오퍼레이션명
├─ called_at      TIMESTAMP
├─ status         VARCHAR
└─ ※ 월별 집계하여 공사 제출 (로컬서버 저장 신청 조건)
```

회원/로그인은 MVP에서 제외 (코스는 UUID 공유 링크로 대체).

### 5.3 코드 체계 변경 (신규)

설명회 자료 p.5에 **`지역코드조회`와 `서비스 분류코드 조회`가 "26년 폐기 예정"** 으로 명시되어 있으며,
서비스 목록에는 이미 `법정동 코드`와 `분류체계 코드(3Depth)`가 대체 오퍼레이션으로 존재한다.

| 구분 | 폐기 예정 | 대체 |
|---|---|---|
| 지역 | `areaCode` / `sigunguCode` | 법정동 코드 (`lDongRegnCd` / `lDongSignguCd`) |
| 분류 | `cat1` / `cat2` / `cat3` | 분류체계 코드 (`lclsSystm1~3`) |

⚠️ 위 파라미터명은 KorService2 매뉴얼 확인 전 잠정 표기. **1주차에 실제 응답으로 확정할 것.**
6.2의 "동일 카테고리 fallback"이 분류코드 체계에 직접 의존하므로 검증 우선순위가 높다.

## 6. 핵심 도메인 로직

### 6.1 혼잡도 진단

```
입력: attractionId, visitDate, timeSlot
0. has_congestion_data 확인 → false면 진단 불가 응답 + 인근 커버리지 관광지 제안
1. derived_congestion에서 해당 시점 등급 조회 (Redis 캐시 우선)
2. 전국 or 동일 지역 분포 대비 백분위 산출 (배치 C단계에서 사전 계산)
3. 등급 매핑: ~50% 여유 / 50~75% 보통 / 75~90% 혼잡 / 90%~ 매우혼잡
출력: { grade, concentration, percentile }
```

등급 컷은 실데이터 분포 확인 후 조정. 백분위 기반으로 설계해 절대값 스케일 변동에 강건하게 만든다.
컷 조정 시 `derived_congestion`만 재계산하면 되며 원천 재적재는 불필요하다.

### 6.2 대안 관광지 매칭

```
입력: 혼잡 판정된 attractionId, visitDate, timeSlot, maxDistanceKm(기본 15km)
1. raw_related에서 연관 후보 조회
2. PostGIS ST_DWithin으로 반경 내 필터
3. 각 후보의 동일 시점 집중률 조인 → '여유/보통' 등급만 통과
   (집중률 커버리지 밖 후보는 이 단계에서 자동 탈락)
4. 스코어링: score = w1·연관도 + w2·(1-집중률정규화) + w3·(1-거리정규화)
5. 상위 N개 반환
```

- 연관도(`relation_score`)가 API에서 제공되지 않을 경우 → w1 항을 제거하고
  w2/w3 2항 스코어링으로 축소, 또는 "연관 목록에 포함되었는가"를 이진 가중치로 대체.
- 후보 부족 시 fallback: 동일 분류체계 + 반경 내 관광지를 TourAPI 위치기반(최대 20km)에서 보충.
  추가 폴백으로 `기초 지자체 중심 관광지 정보`(260,236건) 활용 검토.

### 6.3 우회 코스 구성

```
입력: 원 목적지 + 선택된 대안지 목록, visitDate
1. 장소별 시간대 집중률 프로파일 조회
2. 그리디 배치: 각 시간대 슬롯(오전/점심/오후/저녁)에
   해당 슬롯 집중률이 가장 낮은 장소를 우선 배정
3. 이동 동선 보정: 인접 슬롯 간 거리(ST_Distance)가 임계치 초과 시 순서 스왑
4. (선택) Claude API로 슬롯별 배치 사유 문장 생성
출력: 시간대별 방문 순서 + 사유
```

TSP 최적화 등은 과설계. 슬롯 4개 수준에서는 그리디 + 스왑 보정으로 충분하다.

## 7. 성능·캐싱 전략

| 대상 | 전략 | 근거 |
|---|---|---|
| 집중률 예측 데이터 | 일 1회 배치 적재, Redis TTL 24h | 예측치라 일 단위 갱신으로 충분 |
| 관광지 마스터·연관 관계 | 주 1회 동기화 | 변동 빈도 낮음 |
| 파생 테이블 | 원천 적재 직후 재계산 | 등급 컷 변경 시 단독 재실행 가능 |
| 추천 결과 | Redis 캐시 key: attractionId+date+slot, TTL 6h | 동일 조건 반복 요청 대응 |
| 배치 실패·미적재 fallback | CompletableFuture로 외부 API 병렬 호출 | 순차 대비 응답시간 단축 |
| 외부 API 장애 | Resilience4j Circuit Breaker + 캐시 스냅샷 응답 | 전일 데이터로 서비스 지속 |

목표 지표: 추천 API p95 응답 300ms 이하 (캐시 히트 기준), 외부 API 장애 시에도 전일 데이터로 서비스 지속.

### 7.1 트래픽 예산 (수정)

설명회 자료 p.41 명시: **"일일 트래픽 오퍼레이션별 1,000건 제한"** — 계정 총합이 아니라 **오퍼레이션 단위**다.

| 계정 | 오퍼레이션별 일일 한도 |
|---|---|
| 개발계정 | 1,000건 |
| 운영계정 | 100,000건 |

따라서 집중률조회 / 지역기반관광정보 / 상세조회 등을 각각 1,000건씩 사용 가능하며,
개발계정 단계에서도 배치 적재 예산이 기존 가정보다 여유롭다.
그럼에도 배치 구조를 유지하는 이유는 쿼터가 아니라 **장애 격리와 응답 지연 제거**에 있다.

## 10. 행정 절차 및 준수 사항 (신규)

### 10.1 TourAPI 로컬서버 저장 신청

본 서비스는 **API를 직접 호출하는 방식이 아니라 관광정보를 서버에 저장 후 서비스하는 구조**이므로,
공사에 「TourAPI 로컬서버 저장 신청서」를 제출해야 한다.

자료 명시 조건:

- 로컬서버 저장 이후 콘텐츠 동기화는 **신청기관 책임**이며, 동기화 지연으로 발생하는 문제에 공사는 책임지지 않음
- 신청기관은 **월별 API 호출 실적을 집계하여 월 1회 공사에 제공**해야 함
- **동기화 계획이 제대로 이행되지 않을 경우 해당 서비스는 차단될 수 있음**

### 10.2 동기화 계획 (신청서 제출용)

| 데이터 | 주기 | 방식 | 실패 시 |
|---|---|---|---|
| 집중률 예측 | 일 1회 (03:00 KST) | 전량 UPSERT | 3회 재시도 후 알림, 전일 스냅샷 유지 |
| 관광지 마스터 | 주 1회 (일요일 04:00) | `modifiedtime` 기준 증분 | 다음 주기 전량 재동기화 |
| 연관 관광지 | 주 1회 (일요일 05:00) | 전량 UPSERT | 상동 |
| 호출 실적 집계 | 월 1회 (매월 1일) | `api_call_log` 집계 리포트 생성 | — |

원천 데이터는 무가공 보존하며(5.1), 서비스 로직은 파생 테이블만 참조한다.

### 10.3 운영계정 전환

개발계정만으로는 실서비스 운영이 불가하며, 운영계정 전환 절차가 필요하다.

승인 요건:

1. 개발계정으로 테스트 로그 확인
2. 파라미터 `MobileApp` 값에 서비스 고유명 확인 → `hanjeok` 고정 (4.1)
3. 앱/웹에서 OpenAPI 적용 확인 (서비스 URL 등록 → 심의)

주의:

- 승인 결과는 **회원가입 시 등록한 이메일로 통보**되며, 심의 소요 기간은 자료에 명시되어 있지 않다.
- 따라서 **배포 완료 후 공모전 제출 사이에 심의 버퍼를 확보**해야 한다 (10장 일정 반영).
- 서비스 활용 신청은 **2년 경과 시 유효기간 종료** → 필요시 연장 신청.

### 10.4 위치기반서비스 사업 신고 해당 여부

자료상 위치기반서비스사업자 예시는 배달앱, 택시 호출, 주변 맛집 추천, 위치 기반 광고, 출퇴근 기록 서비스다.

**한적의 판단**: 사용자 단말의 GPS 위치정보를 수집하지 않고,
**사용자가 선택한 관광지 좌표를 기준점으로** 반경 검색만 수행하므로 신고 대상에 해당하지 않는 것으로 본다.

→ 이 전제를 유지하기 위해 MVP에 "내 주변 관광지" 기능을 포함하지 않는다.
향후 GPS 기반 기능 추가 시 위치기반서비스사업 신고 검토가 선행되어야 한다.

## 11. MVP 범위 및 개발 일정 (1인 기준)

### MVP 포함

- 관광지 검색 + 혼잡도 진단 (시간대별)
- 대안 관광지 추천 (연관도 + 집중률 + 거리 스코어링)
- 우회 코스 생성 + 지도 시각화 + 공유 링크

### MVP 제외 (2차 확장)

- 회원/로그인, 코스 저장 목록
- LLM 코스 설명문 (규칙 기반 문장으로 우선 대체)
- GPS 기반 "내 주변" 기능 (10.4 사유)
- 다국어, 앱(React Native) 확장

### 일정 (주말·평일 저녁 기준 약 6주 + 행정 버퍼)

| 주차 | 작업 |
|---|---|
| 0주 | **로컬서버 저장 신청서 제출**, 개발계정 발급, 스파이크 |
| 1주 | 공공 API 스펙 검증(부록 B), 샘플 수집, 스키마 확정, 원천 배치 구현 |
| 2주 | 파생 배치(등급화) + 혼잡도 진단 로직, 진단 API |
| 3주 | PostGIS 대안지 매칭 + 스코어링, 추천 API |
| 4주 | 코스 생성 로직, Next.js 검색·진단 화면 |
| 5주 | 지도 코스 시각화, 코스 상세·공유 |
| 6주 | 캐싱·장애 대응 마감, 배포, **운영계정 신청**, 기능설명서 작성 |
| +α | 운영계정 심의 대기 (기간 미상 — 버퍼 필수) |

행정 절차(로컬서버 저장 신청, 운영계정 심의)는 승인 대기 시간이 있으므로 **개발과 병렬로 최대한 앞당겨 착수**한다.

해시태그 후보 — #혼잡도 분석 #과밀지역 우회 #숨은 명소 #코스 추천 — 를 기능 단위와 1:1 매핑되도록 6장 로직 구조를 유지할 것.

## 13. 공모전 어필 포인트 요약

1. **공공데이터 3종 융합** — 집중률 예측(진단) × 연관 관광지(대안) × TourAPI(콘텐츠)의 유기적 결합
2. **시점 기반 추천** — 장소만이 아니라 "언제 가야 덜 붐비는지"까지 코스에 반영
3. **운영 가능한 설계** — 공공 API 제약 조건 하에서 100ms 내 응답하고 외부 API 가용성과 무관하게 동작하는 서비스.
   배치 적재 + 캐싱 + 서킷브레이커, 그리고 공사 규정을 준수하는 원천/파생 분리와 동기화 계획까지 설계에 포함
4. **과제 취지 정합성** — 오버투어리즘 "분산"이라는 정책 목표를 개인 여행자의 실익(쾌적한 여행)으로 번역
